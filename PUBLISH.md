## Why this flow is dead

| branch | version | registry | state |
|---|---|---|---|
| `master` (default) | 3.0.2 | pub.dev (no `publish_to` before this change) | 3.0.2 already live (2026-11-13) → duplicate-version rejection |
| `development` | 3.1.1 | `https://pub.zuzu.dev` | **already published** (2026-08-23, `4ca0beb`) — nothing new to ship |

- `development`'s dependency graph no longer resolves either: its
  `dev_dependencies` pin `zorphy` at `ref: development`, a git ref that no
  longer exists on `arrrrny/zorphy` (`git ls-remote` has no such branch), so
  that branch is unbuildable independently of the registry question.
- The old auto-generated configuration below described a flow that no longer
  matches reality (it claimed `Public packages: vendure (published to
  pub.dev)` / `Private packages: None`, contradicting `development`'s
  `publish_to: https://pub.zuzu.dev`) and listed no `scripts/release.sh`,
  so every version bump was an operator manual step.

## What publishes instead

Everything on the `vendure` package name publishes from
[arrrrny/zuraffa_vendure](https://github.com/arrrrny/zuraffa_vendure) per its
own `PUBLISH.md` (fleet mono-version policy:
`../zuraffa/scripts/update_fleet.sh <version>`).

Forklift note: with `publish_to: 'none'` set on the default branch, a
`Publish arrrrrny/vendure-flutter-sdk` task can no longer ship anything — the
publish agent's preflight (`dart pub publish --dry-run` followed by the real
command, which now refuses) fails closed and the task settles blocked instead
of forcing a regressive release.
